# 导购 Agent 与搜索推荐链路：开发说明

对应代码：`server.mjs`（`converse()` 编排）、`lib/agent.mjs`（模型调用与校验）、`lib/nlu.mjs`（规则解析）、`lib/engine.mjs`（召回、过滤、排序、求解）、`lib/assistant.mjs`（会话、对比、回复组织）。

## 1. 一轮对话的执行顺序

```
用户一句话
 └─ turn()                  规则解析 + 求解，得到基准结果
     ├─ 看不懂 / 是新需求且带场景
     │   └─ understand()     场景、品类规划、偏好、改写
     │       └─ turn(改写)   改写后的句子再走一遍规则；仍看不懂则保留原追问
     ├─ 推荐结果 + 有场景
     │   ├─ embed(场景)      场景向量 × 商品向量 → 语义加减分
     │   ├─ rerank()         预算内前 4 名候选的场景匹配分
     │   └─ turn(boost)      带加减分重新求解；需求与预算须与基准一致才采用
     ├─ 带商品提问且规则看不懂
     │   └─ answer()         只根据这件商品的数据回答
     └─ narrate()            开场、理由、差异、小提示、追问
```

每一步失败或超时都直接跳过，保留上一步的结果。

## 1.1 哪些话会走模型

| 用户这句话 | 理解与规划 | 语义召回 + 精排 | 讲解 |
|---|---|---|---|
| 新需求且带场景、人群或偏好（“宿舍用的吹风机，别太吵”） | 走 | 走 | 走 |
| 只说目标、没说买什么（“出差一周配数码装备”） | 走（规划品类） | 走 | 走 |
| 规则看不懂的口语（“给我妈整个能刷牙的电动的”） | 走（改写后交回规则） | 有场景时走 | 走 |
| 只有品类和预算（“吹风机，300以内”） | 不走 | 不走 | 走 |
| 在对话里改购物车（“去掉吹风机”“便宜一点”“买两个”“锁定这款”） | 不走，规则直接处理 | 不走 | 回复是推荐时走 |
| 购物车页按钮操作（数量、锁定、换一款、改预算） | 不走 | 不走 | 不走 |
| 对比同类 | 不走 | 不走 | 走（差异解读） |
| 带商品提问且规则看不懂 | 不走 | 不走 | 走（商品问答） |

判断“带场景”：去掉品类名、金额、数量词和常用虚词后仍剩下至少 2 个字（`sceneResidue()`）。

## 1.2 过程实时推送

`POST /api/chat/stream` 与 `POST /api/chat` 参数相同，返回 `text/event-stream`，每个环节开始和结束各推一条事件：

```
data: {"type":"step","status":"running","id":"recall","label":"召回商品"}
data: {"type":"step","status":"done","id":"recall","label":"召回商品","detail":"吹风机：商品池 20 款 → 在售且符合条件 13 款 → 单件不超预算 8 款","at":4300,"ms":2}
data: {"type":"done","conversationId":"…","reply":{…},"plan":{…}}
```

| id | 名称 | detail 内容 |
|---|---|---|
| `read` | 读取需求 | 规则解析出的品类、数量、总预算 |
| `understand` | 理解场景与意图 | 场景、偏好 |
| `plan` / `rewrite` | 拆解目标 / 改写需求 | 规划的品类及理由，改写后的解析结果 |
| `recall` | 召回商品 | 每件：商品池数量 → 在售且符合条件 → 单件不超预算 |
| `semantic` | 语义匹配 | 与场景最贴近的商品 |
| `rerank` | 场景精排 | 每个候选的匹配分与依据 |
| `solve` | 组合求解与核算 | 比较的组合数、选定商品、合计与预算关系 |
| `compare` / `answer` | 找同类对比 / 查看商品信息 | 对比项数、商品页写明的信息 |
| `compose` | 组织回复 | 讲解是否通过核对 |

所有数字都来自这一轮真实执行的结果；只走规则时同样推送读取、召回、求解等步骤。出错时推送 `{"type":"error"}`。整轮记录保存在 `reply.trace`（`steps`、`ms`），历史对话里折叠成“已思考 · 用时 N 秒 · N 步”。

前端（`public/js/api.js` 的 `stream()`、`chat.js` 的 `thinking()`）按约 180ms 一条依次展示，事件堆积时加快；浏览器不支持流式读取时退回 `/api/chat`。反向代理需对该路径关闭缓冲（`docker/nginx/default.conf.template` 已配置）。

## 2. 各环节的接口与约束

| 函数 | 输入 | 输出 | 校验 |
|---|---|---|---|
| `understand(text, state, catalog)` | 原话、规范化数字、当前购物车、可买品类 | `{rewrite, plan, scene, prefs}` | 改写和规划理由中的数字必须出现在原话中；品类必须在可买品类内；有规划时品类一定写入改写句 |
| `embed(texts)` | 文本数组 | 256 维向量 | 失败返回 null，链路不使用语义分 |
| `rerank(scene, groups)`（每件商品一次、并行） | 场景、每件商品的候选（id、标题、价格、参数、卖点） | `{id: {fit, why}}` | id 必须在候选里；fit 为 0–3 的整数；依据中的数字须出自候选数据 |
| `narrate(text, reply, state)` | 推荐 / 对比 / 价位结果 | `{lead, points, tip, ask}` | 逐段校验，不合格的段落丢弃；开场不合格则整体不用 |
| `answer(text, product)` | 问题、商品数据 | 回答文本 | 同上 |

通用校验（`grounded()`）：数字按完整数字匹配，必须出现在给定数据中；禁用词表（`lib/banned.mjs`）与无依据断言词不得出现；`withinBudget` 为假时不得出现“在预算内”等表述。

## 3. 加减分

- 语义分：同一件商品的候选里，相似度做标准化，`z × 60`，截断到 ±120。
- 精排分：`(fit − 1.5) × 120`。
- 合计在 `candidatesFor()` 里截断到 ±400，加到参数分上；参数分量级约 0–2000。
- 加减分只影响已通过过滤的候选的先后，组合求解、运费合并和预算判定不变。

## 4. 数据文件

| 文件 | 生成方式 | 用途 |
|---|---|---|
| `data/catalog.json` | `scripts/sku/` | 商品池 |
| `data/embeddings.json` | `node --env-file=.env scripts/agent/embed_catalog.mjs` | 语义召回；商品池变化后需重新生成 |
| `data/posts.json` | `python3 scripts/posts/xhs_posts.py data/posts.json` | 体验页签与“大家怎么说” |

## 5. 配置

| 变量 | 说明 |
|---|---|
| `AGENT_API_KEY` | 语言服务密钥，只放服务端环境变量；不设置时整条链路退回规则 |
| `AGENT_MODEL` | 模型名（可选） |

## 5.1 如何确认线上在用模型

- `GET /healthz` 返回 `agent: true` 表示服务端已配置密钥。
- `POST /api/chat` 的回复里：`reply.ai.scene`（场景理解）、`reply.ai.plan`（品类规划）、`reply.ai.semantic`（是否用了语义召回）、`reply.ai.considered`（精排候选数）、`reply.ai.reasons`（精排依据）、`reply.agent`（讲解）。这些字段只有模型调用成功才会出现；只走规则时回复里只有 `reply.opening` 这类固定文案。
- 页面上：回复顶部的过程卡片展开后出现“理解场景 / 目标规划 / 语义召回与精排”，推荐商品带绿色“契合场景：…”标签。

## 6. 评测

- 确定性部分：`npm test`、`npm run bench`、`npm run bench:shift`、`npm run scan:copy`、`npm run e2e`，均不依赖模型。
- 模型参与部分：`BASE=<服务地址> node scripts/agent/eval.mjs`，覆盖目标规划、场景精排、口语改写、无关输入，检查预算识别、规划品类、不越预算、禁用词与响应时长。上线前在本地和每个部署地址各跑一遍。

## 7. 性能

单轮典型耗时：规则 < 50ms；理解约 1 秒；语义向量约 0.3 秒；精排 1–3 秒；讲解 1.5–3 秒。多件目标规划最长约 12 秒。Vercel 函数上限设为 30 秒。
