# 知选 bad case 基准

`badcase-benchmark.json`：99 条多轮对话用例，只含输入与可机检断言，不依赖具体商品名。覆盖预算解析、数量、锁定、视图、无解、价格、注入与复制等场景；每条用例的 `why` 字段说明它防止的具体缺陷。

## 分组

| group | 条数 | 防什么 |
|---|---|---|
| budget | 14 | 中文/简写/区间/左右/千分位/外币/负数/零/三位小数/溢出/自我更正/后补预算 |
| multi | 5 | 不搭清单被拒、多件被截断、同品类不同商品被合并、键盘鼠标同品类仍分行 |
| qty | 8 | 两副/2个/×3/一打/十一，小数与零数量被截断或变 1 |
| hard | 5 | 硬条件被静默吞掉、参数缺失被当成满足、推断写成事实 |
| pref | 4 | 偏好被当硬条件筛空；硬条件无解时被静默放宽 |
| edit | 10 | 去掉/加/只要/换成/改数量误删他项、重复新增、删不存在项、“挑一件”“不要了”指代不明 |
| lock | 5 | 改预算/换件/无解时锁定被替换或静默解锁 |
| view | 4 | “按单品看/先只看”被当成改需求；“只买”未改清单 |
| nosol | 3 | 无解时静默提预算、删项或给预算内标签 |
| extreme | 4 | 1 分、1 元、百万、近亿元预算 |
| offcat | 4 | 目录外品类硬凑；部分目录外被静默丢弃 |
| input | 6 | 空输入、乱码、emoji、超长、英文、脚本回显 |
| inject | 5 | 注入突破预算、伪系统指令、泄露提示词、伪指令解锁 |
| price | 4 | 价格当实时价、运费补 0、资格未确认的券计入预算 |
| dup | 3 | 补充描述被拆成多行；无数量的重复点名被静默合并/翻倍 |
| conflict | 3 | 矛盾需求任取其一、最低价断言、价格下限超预算 |
| brand | 3 | 排除品牌仍推荐、品牌偏好导致无解、品牌硬条件被放宽 |
| gift | 5 | 每件预算未换算成总价；多人口径不明未澄清 |
| copy | 4 | 寒暄、解释、真伪追问中出现内部/讲解用词或编造热度 |

## 运行方式

每条用例从**全新会话**开始，按顺序发送 `turns`，断言只针对**最后一轮**的回复文本与结构化状态（`{items, budgetCents, preferences}` 与结果对象）。

## 判定规则

`expect` 中未出现的键不检查。

- `status`：最后一轮结果类型，`recommend` / `clarify`（追问或不理解时请用户补充）/ `reject`（不支持或拒绝执行）/ `no_solution`（理解清楚但按当前条件无可行方案）。
- `budgetCents`：结构化预算（整数分）严格相等；`null` 表示必须没有有效预算，不能是 0 或其他数。
- `itemCount`：购物项**行数**（不是总件数）。
- `items`：按多重集比较（与顺序无关），每行 `qty` 严格相等；`category` 匹配规则：期望名与实际品类名互为子串，或命中目录别名即可（“键盘”可匹配“键盘鼠标”，“手环”可匹配“手表手环”）。`category: null` 表示该行只校验数量、不校验品类（如手冲壶归哪个品类由目录决定）。
- `mustNotContain`：回复全文（含商品卡等渲染文本）区分大小写的子串不得出现。每条已包含通用禁词（演示、样例、demo、mock、合成、原型、约束、文档、策略、求职、测试、本地规则、大模型、undefined、NaN、[object Object]）与无依据断言词（最优、最省、最低价、全网最低、大家都买、销量、爆款、好评率、历史最低）。若将来求解器确实证明最优，需对相应用例单独豁免，不得全局删词。
- `mustContain`：回复必须出现的子串（如移除项名称“耳机”、未知参数的“不能确认”、价格说明的“以平台为准”）。这些是回复文案中的固定锚点；改文案时同步改这里，不放宽语义。
- `totalWithinBudget`：仅当 `status=recommend` 时有。若方案所有费用（商品价×数量+运费等必付项）已知，必须 `总额 ≤ budgetCents`；若有任一费用未知，改判为：回复不得出现“预算内”“符合预算”标签，且结果对象不得标记预算合规。
- `keepsPrevious`：本轮结束后的 items（含 qty、hard、match）、budgetCents 与上一轮完全相同。
- `locked`：列出的品类行必须仍为锁定状态，且所选商品 ID 与锁定发生时相同。

## 已知不可机检项（需人工或另行检查）

- 回复结构是否符合“寒暄 → 选购要点/避坑 → 最适合你 + 理由 → 商品卡 → 备选”。
- 推荐理由是否只引用已有事实、是否把推断写成已核验（只能用 `mustNotContain` 抓典型说法）。
- 偏好是否真的影响了排序（需对照同请求去掉偏好后的结果）；超高预算是否隐性奖励花满。
- 硬条件三态（满足/不满足/未知）是否在商品卡上正确标注；`hard[]` 未纳入断言键，需引擎单测覆盖。
- 澄清问题是否“最少且必要”、无解说明是否给出可选动作（提高预算/去掉某项/放宽条件）。
- 价格观测时间、来源链接、运费未知文案依赖实际目录数据：`price` 组和 `totalWithinBudget` 的费用完整性分支需要一个含“运费未知”商品的目录夹具才能稳定覆盖。
- 英文输入（input-05）只要求不崩溃、不乱填金额，是否支持英文由产品决定。
- 搜索状态（未穷尽不得称“全局无解”）需在引擎层注入截断/超时验证，对话基准无法稳定触发。
- 界面静态文本的禁词由 `test/scan-copy.mjs` 扫描 `public/` 与服务端文案负责，本基准只检查对话回复。

## 与模型参与部分的关系

本基准在没有配置语言服务的环境下运行，覆盖的是规则解析、求解和预算判定这些确定性环节，结果可复现。模型参与的理解规划、语义召回、场景精排和讲解由 `scripts/agent/eval.mjs` 对运行中的服务做端到端检查，见 `docs/agent-pipeline.md`。
